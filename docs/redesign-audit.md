# Аудит перед редизайном (макеты `design/mockups/C-*.dc.html`)

Дата: 2026-10-06. Источник истины — макеты C-*. Код прочитан, ничего не запускалось.

Статусы:
- **ЕСТЬ** — логика уже есть, нужен только новый UI поверх неё;
- **UI** — чистая вёрстка/анимация, логики почти нет;
- **КЛИЕНТ** — нужна новая или изменённая логика в приложении;
- **СЕРВЕР** — нужна правка сервера (см. раздел 2, номера S1…S10).

Коротко: модель данных покрывает почти всё (дела, повторы, конец, «кто», планы, напоминания, «посмотрели», «подарено»).
Серверу не хватает: кто подарил и отметка чужой хотелки (S1), архива тем (S2), даты конкретного повтора в голосовых правках (S3),
вопроса «что **я** делаю» (S4), версии клиента (S5), счётчика голоса (S6). Основная работа — клиентская раскладка календаря.

## 2. Изменения сервера (всё совместимо со старым приложением)

### Три правила

- **П1. Отсутствующее поле — не трогать.** Старое приложение шлёт фиксированный набор полей (`mobile/src/lib/sync.ts`: `taskOp`,
  `wishOp`, `topicOp`), а сервер собирает запись заново (`task.put`: `...op.task`; `wish.put`: `...op.wish`; `topic.put` — явный объект).
  Без П1 любая правка из старого приложения **сотрёт** новые поля. Правило: `undefined` → взять из старой записи, `null` → очистить.
- **П2. Новые поля только `.optional()`.** zod по умолчанию выбрасывает неизвестные ключи, поэтому и старый сервер не падает на запросах
  нового приложения (поля просто не сохранятся). Порядок выката: сначала сервер, потом приложение.
- **П3. Новые типы ответов и новые значения перечислений — только для клиентов с `x-kstati-api >= 2`.** В старом приложении
  `applyResult` (`voice.ts`) — `switch` без `default` (новый тип ответа = тишина), `activityText` вернёт `undefined` для нового
  вида события, `GENRE_LABEL[g]` — `undefined` для нового жанра. Новые необязательные поля в старых ответах гейтить не нужно.

## 4. Риски и открытые вопросы

**Риски:**
- **Без П1 старое приложение сотрёт новые поля** (`giftedBy`, `archivedAt`) любой правкой. Это главный риск, покрыть тестом.
- **Два приложения на одном телефоне:** напоминания локальные (`lib/notify.ts`), поэтому будут **приходить дважды**.
  Плюс одна схема `kstati://` у двух приложений → вход через VK может открыть не то приложение (S8). Нужен план перехода (попросить удалить старое?).
- **Выкат:** сервер раньше приложения; новое приложение проверяет `/health.api >= 2`.

**Открытые вопросы:**
- **Цвета:** одна карта на всех людей требует правила, что делать, если у двоих один и тот же выбранный цвет (кто уступает?).
- **Сюрприз:** видит ли владелец отметку «подарено» и «от кого» сразу? Если да — чекбокс у дарителя раскрывает подарок заранее.
- **Архив чужой общей темы:** только у владельца или личный архив у каждого (тогда только на клиенте)?
- **«Все в группе»:** снимок участников на момент сохранения (как сейчас) или «все, включая будущих»? Второе — новое поле на сервере.
- **Занятость:** считаются ли дела «весь день» и многодневные занятостью для конфликтов и свободных окон? По макету C-AskWeekend — нет (Дача весь день, а окно с 18:30).
- **«Перенеси только этот раз»:** в ленте появятся две записи (удалён один раз + новое дело) — нормально?
- **Голос:** несколько записей в одной фразе и выбор из нескольких кандидатов (до 3) в макетах C-Voice/C-Ask* не показаны.
- **Язык «АВТО»:** проверить, что SpeechKit v1 его поддерживает. Промпт на русском: английские фразы будут разбираться хуже — нужен ли язык в первой версии?
- **Алгоритм пересечений** в макете считается по пикселям (O(n²·высота)). В RN — по границам интервалов; нужны тестовые наборы из C-Week (3 человека, гость дольше основы).
