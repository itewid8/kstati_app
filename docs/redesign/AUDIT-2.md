# Аудит макетов «Инструмент» (C-*.dc.html) против текущей реализации

Что сравнивалось: `design-ref/boards/C-*.dc.html` (разметка и `renderVals()`), с одной стороны, и `mobile/` и `server/` в их нынешнем виде, с другой. Новое приложение `mobile-prod/` (ru.kstati.app, «Кстати β») работает с тем же сервером, что и старое `mobile/`. Поэтому каждое изменение сервера проверено на поведение старого клиента.

Как классифицированы функции:
- **(a)** только UI поверх существующих данных и логики;
- **(b)** нужна новая логика на клиенте, данные и API прежние;
- **(c)** нужно менять сервер, API или модель данных.

---

## 0. Итог

1. Модель данных почти целиком уже есть. Длительность и многодневность (`endDate`/`endTime`), «Кто» (`people`), общее дело с подзадачами (`parentId`, один уровень вложенности проверяет сервер), повторы (`repeat`, `doneDates`, `skipDates`), напоминания «для меня / для всех» (`prefs.overrides` / `task.reminders`), цвет человека (`user.color`), категории групп, «подарено» (`receivedAt`), «посмотрели» (`watchedAt`), темы идей с доступом для групп. Проверка занятости и «вне дат плана» уже работают на клиенте (`TaskEditor.tsx`: `conflicts`, `outside`).
2. Чего на сервере нет совсем: **«от кого подарено»** (C-Wishes) и **архив тем** (C-Ideas). Для голоса нужно точнее: **конкретный раз повтора** (C-AskDelete) и **«что я делаю»** (C-AskWeekend). Для настроек: **язык распознавания** и **счётчик голосовых команд за день** (C-Settings).
3. Главный риск обратной совместимости. Сервер собирает запись **целиком из операции** (`task.put`, `wish.put`, `topic.put` в `server/src/api.ts`), а zod отбрасывает неизвестные ключи. Старый клиент шлёт поля по белому списку (`taskOp`/`wishOp`/`topicOp` в `mobile/src/lib/sync.ts`). Значит, любую правку старым клиентом **стирает новые поля**, если сервер не будет явно переносить их из старой записи (паттерн «merge-preserve», §3.1).
4. В старом клиенте два `switch` без ветки `default`. Если в голосовом ответе придёт новый `ParseResult.type`, человек молча ничего не увидит (`applyResult` в `mobile/src/lib/voice.ts`). Если придёт новый `PlansScope.kind`, будет **исключение**: в `resolveGroups` (`mobile/src/lib/plans.ts`) неизвестный kind попадает в ветку `people`, и `for (… of sc.names)` даёт TypeError. Поэтому новые kind и type вводятся только опциональными полями или за флагом версии (§3.2).
5. Самая тяжёлая клиентская часть — раскладка недели (основа и гость, уступы, 3 уровня вложенности). Нынешний `TimeGrid.tsx` раскладывает пересечения дорожками по людям (`byPeople`). Это другой алгоритм, его надо писать заново (§4.1).

## 2a. Темы, на которые просили обратить особое внимание

- **Общее дело (план) и подзадачи.** Модель: `Task.parentId`, один уровень (сервер обнуляет `parentId`, если у родителя он сам есть). У плана **свой** период (`date…endDate`). `shiftChildren` двигает подзадачи вместе с планом, `syncParent` отмечает план, когда сделаны все подзадачи. «Вне дат плана» = `outside` в `TaskEditor.tsx`. Чего не хватает: в неделе план только полосой (сейчас `band`), подпись «· Общее дело» у подзадачи, обратная проверка «вне периода» при правке периода. Серверу менять нечего.
- **Кто.** `Task.people` (сервер оставляет только участников группы); пусто — автор (`peopleOf`). «ВСЕ В ГРУППЕ» — снимок (b). Занятость каждого участника (b).
- **Пересечения.** `overlaps()` (`lib/span.ts`) уже не считает занятостью дела без времени. Раскладка недели — новая (§4.1).
- **Повторы.** Модель полная (`Repeat`, `occurrences`, `instance`, `nextOpen`, `skipDates`). Голосу не хватает указания на конкретный раз (S3).
- **Напоминания «для меня / для всех».** Полностью есть: личные в `prefs.overrides[taskId]`, общие в `task.reminders`, порядок `effectiveSpecs`: личные → общие → по умолчанию. Срабатывания: `notify.ts` `triggersFor`.
- **Хочу: «подарено», вкладки людей и «ВСЕ».** `receivedAt` есть; «ВСЕ» — клиент (b); «от кого» — S1 (c).
- **Смотреть: «посмотрели».** `watchedAt` есть (a).
- **Идеи: темы и «архив».** Темы, доступ группам, «Без темы» — есть. Архив — S2 (c).
- **Голос.** Создать — `items` (a). Удалить — `changes/delete` (a), один раз повтора — b + S3. Перенос с правкой — `changes/update` с `date/time/people/end` (a), занятость — b. «Что на неделе» — `queryPlans` (a), раскладка по дням — b. «Что на выходных» — `queryPlans` + S4 + свободные окна (b).
- **Категории групп.** Совпадают с `CATEGORIES` на сервере и в клиенте (a).
- **Цвет пользователя.** `User.color` (палитра или `#rrggbb`), операция `profile` (a).
- **Вход по коду из письма.** Регистрация и сброс по коду есть (a). Вход без пароля — S8 (опционально).

## 3. Изменения сервера

### 3.1. Общие правила совместимости (проверено по коду)

Как старый клиент обращается с ответами сервера:
- `/sync`: из записей вырезаются только `type`/`updatedAt` (`kind` у идей), всё остальное сохраняется в store как есть (`sync.ts` `pull`, `replace`). **Неизвестные поля в записях не ломают и не теряются локально.** Неизвестные поля в корне ответа игнорируются.
- `/ops`: старый клиент шлёт поля по белому списку (`taskOp`, `wishOp`, `topicOp`). Сервер собирает запись заново из `op.*`, а zod срезает лишнее. **Вывод: на сервере каждое новое поле обязано переноситься из старой записи, если его нет в операции.**

Паттерн для всех новых полей (`api.ts`, `Data.apply`):
```ts
// zod: newField: Schema.optional()   (undefined = «клиент о поле не знает»)
const keep = <K extends string, T>(incoming: T | undefined, old: Partial<Record<K, T>> | null, key: K): T | undefined =>
  incoming !== undefined ? incoming : old?.[key];
```
Явное `null` от нового клиента означает «очистить», отсутствие поля — «не трогать». Хранилище (YDB Document API, `v` — JSON-строка) схему не меняет: новые поля просто попадают в JSON.

Неизвестные **значения перечислений**, которые старый клиент получил бы с сервера:

| Перечисление | Что сделает старый клиент | Вывод |
|---|---|---|
| `ParseResult.type` | `applyResult` без `default`: голос завершается, карточки нет | Только за флагом `VoiceMeta.v` |
| `PlansScope.kind` | `resolveGroups` → ветка `people` → `sc.names` undefined → **TypeError** | **Не вводить никогда**, только опциональные поля |
| `ActivityKind` | `activityText` возвращает undefined, строка «Имя » без текста | Только за флагом `GET /activity?v=2` |
| `GroupCategory` | `CATEGORY_LABEL[x]` undefined → пустая подпись в `group.tsx` | Не нужно (набор совпадает) |
| `Genre` | `watch.tsx:144` даёт «драма, » с пустым элементом | Низкий риск, косметика |
| `Repeat.freq`, формат `ReminderSpec` | Старый `occurrences`/`moment` дадут неверные даты или `null` | **Не менять**: все пресеты макетов выражаются нынешним форматом |

## 4. Алгоритмы из `renderVals()`, которые нужно перенести на клиент

Чистые функции в `mobile-prod/src/lib/layout/*.ts`, рисование отдельно. Эталонные выходы макетов (контуры, строки) использовать как фикстуры в юнит-тестах.

### 4.1. Неделя: основа и гость (C-Week)
Вход: дела одного дня `{a, b}` в часах, обрезанные по видимому окну `[H0, H0+HN]`. Ширина колонки `Wr = COL − 2`, `WN = 2` (ширина цветной полосы), `G = 2` (зазор), `RAD = 4`, `Gh = G / H` (зазор в часах).
1. Пересекаются `x`, `y`, если это один день и `x.a < y.b && y.a < x.b`.
2. «Основа длиннее»: `longer(x, y) = x.a < y.a || (x.a === y.a && dur(x) > dur(y))`. Это строгий лексикографический порядок (a ↑, dur ↓), циклов нет, рекурсия конечна. `hosts(e)` — пересекающиеся `o` с `longer(o, e)`, `guests(e)` — наоборот.
3. `rightAt(e, t)`: пока активен хотя бы один гость (`t ∈ [g.a − Gh, g.b + Gh]`), правый край = `leftAt(e, t) + WN`, то есть основа сжимается до своей полосы. Иначе правый край `Wr`.
4. `leftAt(e, t) = max по hosts h: envelope(h, t)`, где внутри `[h.a − Gh, h.b + Gh]` значение = `max(rightAt(h, t−Gh), rightAt(h, t), rightAt(h, t+Gh)) + G`, а вне — 0 (в макете короткий «скос» `rampH = 0.01/H`, практически ступенька).
5. Вложенность: `rightAt` вызывает `leftAt`, тот вызывает `rightAt` основ. Три уровня дают отступы 0 → 4 → 8px (ЧТ: Встреча → Тренировка → Отчёт).
6. Контур: левая и правая кромки по строкам → `stepify` (скачок по x превращается в горизонтальную ступеньку) → `simplify` (убрать коллинеарные точки) → полигон. **Внутренние** углы скругляются радиусом `min(4, ½ соседних отрезков)`, верх и низ блока остаются прямыми (гость прямой сверху).
7. Цветная кромка: левый контур (без замыкания) обводкой 4px, обрезанной фигурой, — видно 2px, и полоса повторяет уступы. У двух людей обводка с вертикальным градиентом (верх c1, низ c2), а заливка с горизонтальным c1→c2, `alpha` 0.2 в светлой и 0.24 в тёмной теме.
8. Текст: с первой строки, где левая кромка перестала уменьшаться: `pt = y_j + 3`, `pl = x_j + 6`. Три строки: название (8/600, зачёркнуто, если сделано); время (`HH:MM–HH:MM`, `→ HH:MM`, `HH:MM →`, «весь день»); кто (`· Общее дело` для подзадачи).

Перенос на RN:
- Не сэмплировать по 1px. Контур кусочно-постоянный, меняется только в точках `{g.a−Gh, g.b+Gh}` гостей и `{h.a−Gh, h.b+Gh}` основ. Строить ступенчатый полигон аналитически по этим точкам, а сэмплирование из макета оставить для теста.
- Фигура и кромка — `react-native-svg` (`Path`, `ClipPath`, `LinearGradient`). В RN нельзя обрезать `View` по пути, поэтому ширина текста = `min(rightAt) − pl` по высоте текстового блока, а сам текст лежит в `View` с `overflow: hidden`.
- Нажатие по фигуре: `Pressable` на ограничивающий прямоугольник, порядок наложения — гости выше основ.

Краевые случаи, которые макет не покрывает (**нужно решение**):
- **Одинаковое начало и одинаковая длительность**: `longer` ложно в обе стороны, оба дела рисуются на всю ширину друг поверх друга. Предлагается добивать порядком участников группы, затем `id`.
- **Гость начинается почти одновременно с основой** (меньше ~1 строки текста): заголовок основы не виден, остаётся 2px полоса. Предлагается: если `g.a − h.a < 20px / H`, раскладывать этот кластер равными дорожками, как в C-Day.
- Дела без конца в сетке занимают 30 минут (`DEFAULT_MIN`). Сохранить.
- Многодневное **не**-общее дело со временем: в макете его нет. Предлагается оставить нынешнее правило (полоса и ярлыки в дни начала и конца, `isLong`).

### 4.2. Полосы над сеткой (C-Week, C-Day)
Сортировка `(d0 ↑, d1 ↓)`, строка — первая, где `rowEnd < d0`, иначе новая. Это эквивалент нынешних `segs` в `TimeGrid.tsx`. Сетка начинается под полосами: `GY = BY + nRows·22 + 8`. В макете строк столько, сколько нужно. Сейчас `MAX_ROWS = 3` с «+N». **Предложение**: оставить предел 3 и «+N», иначе неделя с 6 полосами съест сетку. В полосы попадают: дела без времени, многодневные без времени, **общие дела с подзадачами** (в любом случае), а также дела длиннее суток (как сейчас).

### 4.3. Видимые часы (C-Day, C-Week, C-Plan)
`H0 = max(0, min(floor(a_i), floor(now)) − 1)`, `H1 = min(24, max(ceil(b_i), ceil(now)) + 1)`. Для C-Plan `now` не учитывается. В неделе берутся все 7 дней.
- Если дел нет, окно получается около 3 часов вокруг «сейчас». **Предложение**: минимальная ширина 8 часов, центр по «сейчас» или 09–21.
- Многодневные куски, которые идут с 00:00 или до 24:00, считать так, как сейчас (`starts`/`ends` в `TimeGrid.tsx`), иначе окно всегда станет 0–24.
- Высота часа = `GH / (H1 − H0)` без прокрутки. Нижний предел оставить (`MIN_HOUR_H = 16`), чтобы при 0–24 сетка листалась.

### 4.4. Месяц (C-Month)
В клетке 5 строк по 9px. Если `n ≤ 5`, все. Если `n > 5`, первые 4 и «+(n−4)». Порядок как в дне (`sortKey`). Подзадачи показываются, общее дело — только тоном и полосой по верху клеток своего периода. Повторы — через `expandTasks` за месяц.

### 4.5. Год (C-Year)
В макете уровень случайный. Предлагаемое правило: `count` = число дел дня (с повторами); кто = объединение `peopleOf` по делам дня. Если там один человек — его цвет; если несколько — «вместе» (диагональ 135° двух цветов, при трёх и больше — первые два по порядку группы). `alpha = 0.35 + 0.5·min(1, count/4)`. Пустой день — `empty`, сегодня — `red` с ореолом. Счётчики: «214 ДЕЛ» за год и число у месяца — дни или дела (**уточнить**; в макете у месяца это **дни** с делами).

### 4.6. Список голосового ответа по дням (C-AskWeek, C-AskWeekend)
Для каждого дня периода: строки = дела со временем и подзадачи (`time`, `title`, `who`), сортировка по `sortKey`. Многодневные и общие дела становятся заметкой дня начала: `«ЗАГОЛОВОК → ДН»` (день недели последнего дня по `lastDay`), однодневное общее дело — просто `«ЗАГОЛОВОК»`. В C-AskWeekend многодневные и дела на весь день, наоборот, идут строками «ВЕСЬ» и высотой 22. **Решение**: строки при периоде ≤ 2 дней, заметки при более длинном. Счётчик «N ДЕЛ» = число строк.

### 4.7. Свободные окна (C-AskWeekend)
Для каждого дня: занятость = объединение `minutesOn` моих дел (`peopleOf` ∋ me) со временем; дела на весь день **не** занимают (как в `overlaps()`). Окна = дополнение в пределах `[09:00, 23:00]`, длиной от 90 минут. Формат: «СБ 18:30 →» (до конца дня), «ВС ДО 11:00» (с начала дня), «СБ 12:00–15:00» (в середине). В данных макета пропущено окно СБ 10:30–17:00, **данные макета не согласованы**, правило уточнить у дизайна.

### 4.8. Прочее
- Прогресс общего дела: сегменты по числу подзадач, закрашено `doneAt`.
- «Вне периода» у плана: `kids.filter(k => k.date && (k.date < plan.date || k.date > lastDay(plan)))`.
- Занятость участника (C-EditWho, C-AskMove): `tasks.filter(t => t.id !== self && peopleOf(t).includes(uid) && overlaps(t, draft))`, с повторами через `expandTasks` за день черновика (так же, как `conflicts`).
- Колесо времени: см. C-TimeStory. Шаг 5 минут, круговое (`LOOPS`), отклик на каждом шаге.

## 6. Открытые вопросы и несогласованности в макетах

1. **Период плана и `shiftChildren`.** C-EditPeriod показывает «ВНЕ ПЕРИОДА» после правки периода, то есть подзадачи остаются на месте. Нынешний клиент при переносе даты начала плана **сдвигает** подзадачи. Нужно решить: сдвигать (тогда «вне периода» возникает только при сужении) или не сдвигать.
2. **Период в C-Plan (06:00) не совпадает с C-EditPlan (07:00)**: в C-Plan он вычисляется из подзадач, в C-EditPlan задан у дела. Рекомендация: брать период дела.
3. **Термины:** «ОБЩЕЕ ДЕЛО» (C-EditPlan/Period/Year, C-Week) и «ПЛАН» (C-Plan, «ПЛАН СЕТКОЙ», «+ ПЛАН»). Нужно выбрать один, это касается и текстов ленты и голоса.
4. **День** раскладывает пересечения дорожками, **неделя** — основой и гостем (§4.1). Подтвердить, что это намеренно.
5. **ПОВТОР в C-EditPlan** показан, но у плана повтор запрещён (`canPlan`).
6. **«ВСЕ В ГРУППЕ»**: снимок или «всегда все» (S11).
7. Свободные окна в C-AskWeekend не следуют ни одному очевидному правилу (§4.7).
8. Счётчики в C-Year: дни или дела.
9. **Параллельная установка.** Если на телефоне стоят оба приложения под одним аккаунтом, локальные напоминания (`notify.ts`) сработают **дважды**. Предложение: в β напоминания по умолчанию выключены, пока оно в тесте, или показывать предупреждение.
